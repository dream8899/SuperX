# 受控进化协议

## 目的

自我改进只负责收集候选，不拥有修改 Skill 的权限。运行任务、复盘失败或累计次数均不得
自动改写核心规则、脚本、模板、schema、默认参数或 Agent 提示。避免标准漂移、错误经验
累积、单账号特例泛化和模板污染。

## 三层状态

1. **运行状态**：媒体账本、批次报告、审批结果和创作者专属记忆。按既定 schema 更新，
   并存放在业务数据目录；不得写进 Skill 目录或变成全局规则。
2. **学习候选**：仅追加到 `.learnings/` 或 `governance/proposals/`。候选没有执行权，
   不得被模板、脚本或 Agent 自动加载为指令。
3. **受保护核心**：除上述候选与审批目录之外的整个 Skill，包括 `SKILL.md`、
   `agents/`、`references/`、`scripts/`、模板、schema、测试和同步机制。

学习日志不是事实库。一次成功、一次失败、用户临时偏好、某个平台瞬时行为或某个创作者
样本都只能形成候选，不能直接晋升。

## 禁止自动行为

- 不得由钩子、定时任务、批处理、任务结束复盘或“连续出现 N 次”自动修改受保护核心。
- 不得把 `.learnings/` 内容拼接进系统提示、默认 prompt、模板或命令参数。
- 不得让 Agent 自行填写“人工批准”、替用户批准，或把沉默视为批准。
- 不得用新经验弱化授权、源文件保护、预览审批、HOLD、视觉映射、高风险批准、完整验证、
  血缘或回滚要求。
- 不得直接覆盖已安装副本；先修改权威仓库，通过测试，再按既定同步机制分发。

## 候选格式与隔离

候选至少记录：稳定 ID、日期、来源任务、原始证据、适用范围、反例、风险、建议动作和
状态。状态默认为 `candidate`；可改为 `rejected`、`needs-more-evidence` 或
`proposed`。只有维护任务可以把候选整理成提案。

候选不得包含 Cookie、Token、二维码、浏览器 Profile、私人素材内容或临时媒体 URL。
互相矛盾的候选必须并存并标注冲突，不能以“最新一条覆盖旧规则”的方式解决。

## 晋升门禁

修改核心必须是独立、明确的 Skill 维护任务，并按顺序完成：

1. 提交提案：说明当前规则、拟议差异、证据、反例、影响范围、风险、迁移和回滚。
2. 取得人工明确批准。批准只覆盖列出的文件和差异，不授权其他顺手修改。
3. 在修改核心之前，把批准记录单独提交到 `governance/approvals/*.json`。
4. 修改核心并补充或更新测试；先跑最小相关测试，再跑完整 Skill 校验。
5. 运行 `python3 scripts/controlled_evolution_guard.py --approval-file ...`。范围不匹配、
   批准记录与基线不同或记录未预先提交时必须失败。
6. 审查完整 diff，确认没有候选原文、创作者特例或秘密进入模板。
7. 提交、同步已安装副本并推送；保留前一提交作为回滚点。

涉及核心安全边界的修改即使获批也只能保持或增强保护；若确需放宽，必须在提案中逐条列出
被放宽规则、理由、风险和恢复方式，并再次取得针对该放宽的明确批准。

## 批准记录

批准 JSON 至少包含：

```json
{
  "status": "approved",
  "approved_by": "human:NAME",
  "approved_at": "ISO-8601",
  "approval_reference": "明确用户指令或评审记录",
  "scope": ["SKILL.md", "references/example.md"],
  "reason": "为什么要改",
  "risk": "可能破坏什么",
  "rollback": "如何恢复",
  "tests": ["要执行的测试"]
}
```

批准文件必须已存在于基线提交且本次工作树未修改。守卫只验证流程证据，不替代人工 diff
审查，也不能证明批准内容真实；Agent 仍必须遵守“不得伪造批准”的核心规则。

## 不可弱化边界

SuperVideoMix 的授权内容、源文件不覆盖、先计划后审批、高风险显式批准、HOLD、视觉映射、
完整验证和资产血缘均为不可弱化边界。创作者记忆、平台选择器和经验阈值是运行数据或候选，
不得凭任务成功次数自动升级为全局默认。
